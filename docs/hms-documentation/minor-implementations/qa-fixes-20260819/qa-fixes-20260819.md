# QA Fixes — HMS_QA_20260819

Ref: HMS_QA_20260819.pdf (Roll Out Test tenant, `tenant_id=89`)

Four issues were reported from the QA report. Issues 1 and 2 are frontend URDD usage problems. Issues 3 and 4 required backend investigation and fixes. Additionally, two systemic issues were discovered and fixed during the investigation: default unit reservation for unscheduled service slots, and delivery unit resource freeing on booking edits/cancellations.

---

## Issue 1: Payment Initiation Returns 404 "Booking not found"

### Symptom

Room and package bookings create successfully, but `POST /api/guest/payments/initiate` returns:

```json
{
  "status": 404,
  "statusCode": "E50",
  "message": "Failed to initiate payment",
  "payload": { "message": "Booking not found", "source": "Guest Moyasar Payments" }
}
```

### Root Cause — Global URDD Sent Instead of Tenant URDD

The request payload shows `actionPerformerURDD: 720` with `tenantId: null`. URDD 720 is the **global (null-tenant) URDD**.

Booking creation succeeds because `createRoomBooking` / `createPackageBooking` fall back to `hotelId` from the request body when `tenant_id` is null. However, the payment initiation flow relies on `ensureGuestUrdd` to stamp `decryptedPayload.tenant_id` from the URDD. With the global URDD, `tenant_id` stays null and the booking lookup fails.

The payment request only sends `bookingId` — it does not send `hotelId` — so the auto-provision fallback in `ensureGuestUrdd` cannot trigger.

### Backend Mechanisms That Prevent This

Three mechanisms exist to ensure the frontend always has a tenant-specific URDD:

| Mechanism | When | What it does |
|-----------|------|--------------|
| Login reconciliation (`reconcileGuestTenantUrdds`) | Signup and OTP login | Eagerly creates per-tenant URDDs for every active hotel, returns complete `tenantUrddMap` |
| Ensure-URDD endpoint (`POST /api/guest/auth/ensure-urdd`) | On-demand | Creates URDD for a specific hotel if missing, returns updated `tenantUrddMap` |
| Auto-provision fallback (`ensureGuestUrdd`, lines 96-102) | Every authenticated request with `hotelId` | Silently creates tenant URDD when global URDD is sent with a `hotelId` |

### Frontend Fix Required

When making any hotel-scoped API call, use the tenant-specific URDD:

```js
const urddId = tenantUrddMap[String(hotelId)];
if (!urddId) {
  // Call POST /api/guest/auth/ensure-urdd with tenant_id: hotelId
  // Update local tenantUrddMap from the response
}
// Use urddId as actionPerformerURDD in the request
```

No backend changes required.

## Issue 2: Booking Not Showing in Upcoming Bookings

### Symptom

`GET /api/guest/bookings/upcoming` returns `{ items: [] }` immediately after a confirmed booking.

### Root Cause — Same as Issue 1

Request headers show `actionPerformerURDD: 720, tenantId: null`. The upcoming bookings query scopes through the URDD's `tenant_id`. The global URDD has `tenant_id = NULL`, producing no tenant matches, so the query returns zero rows even though the booking exists under `tenant_id = 89`.

The upcoming endpoint does not accept `hotelId` in the request, so the auto-provision fallback cannot help. The frontend must send a tenant-specific URDD.

### Frontend Fix Required

Same as Issue 1.

## Issue 3: Freshly Created Service Shows False Non-Availability

### Symptom

`GET /api/guest/unavailable/dates?packageId=381` returns 19 unavailable dates (Aug 22 - Sep 9) for a service with 2 delivery units where only 1 unit has a single booking (Aug 22 - Sep 4). Dates Sep 5-9 have no bookings at all.

### Analysis

The `fetchUnavailableDates.js` logic is correct for properly migrated data. It counts total active units and marks a date unavailable only when all units are booked (`HAVING booked_units >= totalUnits`).

The likely cause on tenant 89 is that delivery units were created with `location_id` pointing to the zone (`locations.id = 3874`) instead of the `service_locations.id` anchor (2971). This is consistent with the July 2026 migration (`20260706_2_repoint_delivery_units_location_to_service_locations.sql`) either not covering this data or the admin CRUD creating units with the old FK target.

When the join `du.location_id = sl.id` fails, `totalUnits = 0`, and the function returns all 365 dates as unavailable. The frontend displays a truncated subset.

### Backend Change

**File:** `Src/HelperFunctions/PreProcessingFunctions/Guest/fetchUnavailableDates.js`

Added `AND sl.status = 'active'` to the unit count query for consistency with the booking query. Inactive `service_locations` should not contribute to the available unit pool.

## Issue 4: Package Booking Accepts Guests Exceeding Sub-Service Limits

### Symptom

Package 381 includes a gym service (`max_adults=2`). A package booking with `adults: 4` succeeds. The room allows 4 adults, but the gym only allows 2 — the more restrictive limit is ignored.

### Root Cause

`createPackageBooking.js` only validated guest counts against:

- **Stay service**: `min_persons_per_booking` / `max_persons_per_booking`
- **Package-level**: `max_quantity_per_booking`

It did **not** validate `max_adults` or `max_children` for non-stay services included in the package.

### Backend Changes

**File:** `Src/HelperFunctions/PreProcessingFunctions/Guest/createPackageBooking.js`

**1. Config fetch** (line 359-362) — Added `max_adults` and `max_children` to the batch config fetch for all package service IDs:

```js
fetchGuestConfigs("services", allServiceIds, [
  "max_adults",
  "max_children",
]),
```

Runs in parallel with existing package and stay config fetches (no extra round-trip).

**2. Validation loop** (lines 515-542) — After the existing stay-level party size check, iterates all package services and rejects if any service's limit is exceeded:

```js
for (const line of lines) {
  const svcCfg = allSvcCfgMap.get(line.service_id) ?? {};
  const svcMaxAdults = cfgNum(svcCfg.max_adults);
  if (svcMaxAdults != null && adults > svcMaxAdults) {
    throw error 400: "Maximum N adult(s) allowed for included service \"Name\""
  }
  const svcMaxChildren = cfgNum(svcCfg.max_children);
  if (svcMaxChildren != null && children > svcMaxChildren) {
    throw error 400: "Maximum N child(ren) allowed for included service \"Name\""
  }
}
```

Runs before unit picking, so no resources are allocated for invalid bookings.

### Error Messages

The rejection message names the specific service:

```
Maximum 2 adult(s) allowed for included service "Full Body Massage"
Maximum 0 child(ren) allowed for included service "Full Body Massage"
```

### Existing Validation Unaffected

The stay-level `max_persons_per_booking` check (lines 494-508) runs first and is unchanged. Test 7 confirms this continues to work.

## Issue 5: Default Unit Reservation for Unscheduled Service Slots

### Problem

When a service was booked without a specific time slot (unscheduled), no delivery unit was reserved. `pickAvailableSlotUnit` returned `null` for unscheduled slots, and the `booking_service_slots` row was inserted with `unit_id = NULL`. This meant:

- Hotel staff had no visibility into which units were committed
- Availability counts were inaccurate — a fully booked service could still appear available
- The guest could schedule later and find no units left

This affected add-on services, package non-stay services, and standalone service bookings.

### Backend Changes

**File:** `Src/HelperFunctions/Guest/v2/createBookingShared.js`

**1. `pickAvailableSlotUnit` updated** — When `scheduledStart` is null (unscheduled), now picks the first available unit for the service instead of returning null:

```js
// Before: if (!scheduledStart) return null;
// After:
if (!scheduledStart) {
  // Pick the first available unit for this service
  const rows = await executeQuery(
    `SELECT du.unit_id FROM delivery_units du
     JOIN service_locations sl ON du.location_id = sl.id
     WHERE sl.service_id = ? AND du.status = 'active'
     ORDER BY du.sort_order ASC, du.unit_id ASC LIMIT 1`,
    [serviceId],
  );
  return rows[0]?.unit_id ?? null;
}
```

**2. New `resolveEarliestSlot` function** — Queries `unit_availability` for the earliest time window on a given date, returning `scheduledStart` and `scheduledEnd` as full datetime strings. Checks both unit-level and location-level availability windows, respects `day_of_week` and `specific_date` rules.

**File:** `Src/HelperFunctions/PreProcessingFunctions/Guest/createPackageBooking.js`

Non-stay service slot insertion loop now calls `resolveEarliestSlot` for unscheduled slots before picking a unit, using the booking's `checkIn` date as the target date.

**File:** `Src/HelperFunctions/PreProcessingFunctions/Guest/addBookingServices.js`

- `loadBooking` now fetches `check_in_date`
- `insertAddon` accepts a `fallbackDate` parameter and calls `resolveEarliestSlot` for unscheduled slots
- The caller passes the booking's `check_in_date` as the fallback date

### Behavior After Fix

| Slot type | Before | After |
|-----------|--------|-------|
| Scheduled (guest picked time) | Unit picked, assigned | Unchanged |
| Unscheduled (no time yet) | `unit_id = NULL` | Unit picked from pool; time defaulted to earliest `unit_availability` window |
| No availability windows defined | `unit_id = NULL` | Unit picked (no time); same as before but with a unit assigned |

The guest can still reschedule later — the default reservation ensures the unit shows as occupied for management purposes.

## Issue 6: Delivery Unit Resource Freeing on Booking Edits

### Problem

When bookings were cancelled, services removed, or slots rescheduled, delivery units assigned to `booking_service_slots` were not properly freed. This caused phantom occupancy — units appeared booked even after their parent booking was cancelled.

The root cause was that cancellation/removal operations set `status = 'inactive'` on slot rows but did NOT set `slot_status = 'cancelled'`. The availability query in `computeSlots.js` checks **both** conditions:

```sql
-- A unit is occupied when:
WHERE status = 'active' AND slot_status IN ('scheduled', 'completed')
```

Setting only `status = 'inactive'` freed the unit (because the `status = 'active'` filter excludes it), but this was inconsistent and left `slot_status` in a misleading state. More critically, the booking cancel flow did not touch `booking_service_slots` at all.

### Scenarios Fixed

| Scenario | Before | After |
|----------|--------|-------|
| Cancel booking | `booking_items` cancelled; `booking_service_slots` untouched | Both `booking_items` and `booking_service_slots` cancelled |
| Remove service (targeted slot) | `status = 'inactive'` only | `slot_status = 'cancelled'` + `status = 'inactive'` |
| Remove service (bulk) | `status = 'inactive'` only | `slot_status = 'cancelled'` + `status = 'inactive'` |
| Reschedule slot | Times updated; unit NOT reassigned | Times updated; unit reassigned via `pickAvailableSlotUnit` for new time |

### Backend Changes

**File:** `Src/Apis/ProjectSpecificApis/GuestSpecificApis/GuestBookingCancel/GuestBookingCancel.js`

Added slot cancellation in `postProcess` after booking_items cancellation:

```js
await executeQuery(
  `UPDATE booking_service_slots SET slot_status = 'cancelled', status = 'inactive'
   WHERE booking_id = ? AND status = 'active'`,
  [bookingId],
);
```

**File:** `Src/HelperFunctions/PreProcessingFunctions/Guest/removeBookingService.js`

Both targeted and bulk removal now set `slot_status = 'cancelled'` alongside `status = 'inactive'`:

```js
// Targeted (single slot)
`UPDATE booking_service_slots SET slot_status = 'cancelled', status = 'inactive', updated_by = ? WHERE slot_id = ?`

// Bulk (all slots for a service)
`UPDATE booking_service_slots SET slot_status = 'cancelled', status = 'inactive', updated_by = ?
 WHERE booking_service_id IN (...)`
```

**File:** `Src/HelperFunctions/PreProcessingFunctions/Guest/rescheduleBookingService.js`

`updateSlot` now calls `pickAvailableSlotUnit` when timing changes to reassign the delivery unit for the new time window:

```js
if (timingFields.scheduled_start && serviceId) {
  const newUnitId = await pickAvailableSlotUnit(serviceId, newStart, newEnd);
  if (newUnitId != null) {
    sets.push("unit_id = ?");
    params.push(newUnitId);
  }
}
```

The `serviceId` parameter was added to all three `updateSlot` call sites (sessions, meals, transport).

## Issue 7: Token Refresh Does Not Return `tenantUrddMap`

### Problem

The token refresh endpoint (`POST /api/auth/refresh`) only rotated the JWT access + refresh tokens. It did not:

- Call `reconcileGuestTenantUrdds` to back-fill URDDs for tenants added since last login
- Return `tenantUrddMap` in the response

This meant a guest who never logged out (only refreshed tokens) would never get URDDs for new hotels. The frontend's local `tenantUrddMap` would go stale, leading to the global-URDD issues described in Issues 1 and 2.

### Backend Changes

**File:** `Src/HelperFunctions/PreProcessingFunctions/Guest/refreshGuestTokens.js`

Added `reconcileGuestTenantUrdds(userId)` call after the token rotation transaction completes, and included `tenantUrddMap` in the return payload:

```js
const { tenantUrddMap } = await reconcileGuestTenantUrdds(userIdNum);

return {
  accesstoken: accessToken,
  refreshToken: refreshTokenSigned,
  expiresIn,
  tenantUrddMap,  // NEW — keeps frontend in sync
};
```

**File:** `Src/HelperFunctions/PreProcessingFunctions/Guest/reconcileGuestTenantUrdds.js`

Added reactivation of `status='inactive'` URDDs before attempting `INSERT IGNORE`. Previously, if a URDD was soft-deleted (set to inactive), the reconcile would try to insert a new row, hit the unique constraint via `INSERT IGNORE`, and silently skip — leaving the guest without that tenant's URDD. Now it tries `UPDATE ... SET status = 'active'` first:

```js
const reactivated = await executeQuery(
  `UPDATE user_roles_designations_department
      SET status = 'active', updated_at = NOW()
    WHERE tenant_id = ? AND user_id = ? AND status = 'inactive'
    LIMIT 1`,
  [tid, userId], connection, false,
);
if (reactivated.affectedRows > 0) { created.push(tid); continue; }
// fallback to INSERT IGNORE for truly new rows
```

## API Reference: Guest URDD Provisioning

### `POST /api/guest/auth/ensure-urdd`

On-demand URDD provisioning for a single hotel. Called by the frontend when it detects `tenantUrddMap[hotelId]` is missing.

**Platform:** `AUTH_PLATFORM` (AES-ECB with accessToken + platform key)

**Request body:**

```json
{
  "tenant_id": 89
}
```

**Response:**

```json
{
  "urdd_id": 950,
  "tenant_id": 89,
  "created": true,
  "tenantUrddMap": {
    "global": 801,
    "16": 802,
    "63": 803,
    "89": 950
  }
}
```

| Field | Type | Description |
|-------|------|-------------|
| `urdd_id` | number | The URDD ID for this tenant (new or existing) |
| `tenant_id` | number | The requested tenant ID |
| `created` | boolean | `true` if a new URDD was inserted; `false` if it already existed |
| `tenantUrddMap` | object | Complete refreshed map — frontend should replace its local copy |

**Errors:**

| Status | Code | Reason |
|--------|------|--------|
| 400 | — | `tenant_id` not provided |
| 401 | — | No authenticated user |
| 404 | — | Tenant not found or inactive |

**Backend flow:**
1. Validates tenant is active (`status = 'active'`, `is_active = 1`)
2. Resolves the guest RDD for the tenant via `getGuestRddIdForTenant`
3. Checks for existing active URDD — returns it if found (idempotent)
4. Creates new URDD if missing
5. Calls `buildGuestUrddList` to return the complete updated map

**Source:** `Src/HelperFunctions/PreProcessingFunctions/Guest/ensureGuestTenantUrdd.js`

### `POST /api/auth/refresh`

Token rotation with URDD reconciliation. Exchanges an expired access token + valid refresh token for a new pair, and back-fills any missing tenant URDDs.

**Platform:** `PUBLIC_ENCRYPTED_PLATFORM` (AES-ECB with platform key only, no auth)

**Request body:**

```json
{
  "accesstoken": "<expired-access-token>",
  "refreshToken": "<valid-refresh-token>"
}
```

The expired access token can also be sent in the `accesstoken` header.

**Response:**

```json
{
  "accesstoken": "<new-access-token>",
  "refreshToken": "<new-refresh-token>",
  "expiresIn": 900,
  "tenantUrddMap": {
    "global": 801,
    "16": 802,
    "63": 803,
    "89": 950
  }
}
```

| Field | Type | Description |
|-------|------|-------------|
| `accesstoken` | string | New short-lived JWT access token |
| `refreshToken` | string | New rotated refresh token (old one is invalidated) |
| `expiresIn` | number | Access token TTL in seconds |
| `tenantUrddMap` | object | Complete URDD map after reconciliation — back-fills new tenants |

**Errors:**

| Status | Code | Reason |
|--------|------|--------|
| 400 | `access_not_expired` | Access token is still valid |
| 401 | `access_invalid` | Access token signature invalid |
| 401 | `access_expired_beyond_grace` | Access token expired more than 10 minutes ago |
| 401 | `refresh_invalid` | Refresh token invalid or device not found |
| 401 | `token_mismatch` | Access and refresh tokens belong to different users/devices |
| 409 | `refresh_replayed` | Refresh token JTI already used (replay detection) |
| 410 | `refresh_expired` | Refresh token expired (24-hour TTL) |
| 422 | `validation_failed` | Missing required fields |

**Backend flow:**
1. Validates expired access token (must have expired within 10 minutes)
2. Verifies refresh token signature, JTI, and family ID
3. Cross-checks access + refresh belong to the same user/device
4. Rotates tokens in a transaction with row lock on `user_devices`
5. Calls `reconcileGuestTenantUrdds(userId)` to create/reactivate missing URDDs
6. Returns new tokens + complete `tenantUrddMap`

**Source:** `Src/HelperFunctions/PreProcessingFunctions/Guest/refreshGuestTokens.js`

### `reconcileGuestTenantUrdds(userId)` — Internal Helper

Not an API endpoint. Called internally by signup, OTP login, admin guest creation, and token refresh.

**What it does (two-phase, transactional, idempotent):**

**Phase 1 — URDD delta:** For every active tenant (excluding the system tenant), checks if the user has an active URDD. If not:
- Tries to reactivate an existing inactive URDD (`UPDATE ... SET status = 'active'`)
- Falls back to `INSERT IGNORE` for truly new rows
- Binds each URDD to that tenant's guest RDD clone via `getGuestRddIdForTenant`

**Phase 2 — URDP resolve:** For every active per-tenant guest URDD (designation = STANDARD only):
- Syncs permissions from that tenant's `PG-STANDARD-GUEST` permission group
- Scoped to guest-leg URDDs only — never touches staff URDDs the same user might hold

**Called from:**

| Caller | When |
|--------|------|
| `signupGuest.js` | Guest signup |
| `verifyGuestOtp.js` | OTP login |
| `signupGuestSocial.js` | Social signup |
| `adminCreateGuestUser.js` | Admin creates guest |
| `refreshGuestTokens.js` | Token refresh |

**Returns:** `{ created: number[], tenantUrddMap: object }`

**Source:** `Src/HelperFunctions/PreProcessingFunctions/Guest/reconcileGuestTenantUrdds.js`

---

### `tenantUrddMap` Shape

Returned by all auth flows (login, signup, refresh, ensure-urdd). The frontend should store this locally and use it for all hotel-scoped API calls.

```json
{
  "global": 801,
  "16": 802,
  "63": 803,
  "89": 950
}
```

- Key `"global"` — the null-tenant URDD (used for non-hotel-scoped calls)
- Key `"<tenant_id>"` — per-hotel URDD (use as `actionPerformerURDD` for hotel-scoped calls)
- Only includes active tenants (`status = 'active'`, `is_active = 1`)
- Frontend lookup: `tenantUrddMap[String(hotelId)]`

**Source:** `Src/HelperFunctions/PreProcessingFunctions/Guest/buildGuestUrddList.js`
